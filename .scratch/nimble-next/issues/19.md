## Zakres i decyzje
V1 tylko NIM i odbiorca właściciela lokalu. Wystaw rachunek przez klucz z reference i idempotency; GET status, kwoty, sieć i hash po potwierdzeniu. External reference unikalne w lokalu, nie globalnie. Rachunek integracyjny nie wymaga fizycznej zmiany kasjera: oznacz źródło EXTERNAL i zachowaj odrębność sprzedaży pozycji. Nie udawaj katalogowej sprzedaży bez pozycji. Określ limit długości i rate limit przed publicznym udostępnieniem.

## Kontrakt ewidencji wpływu
Potwierdzenie tworzy niezmienny dowód EXTERNAL_RECEIPT przypisany do rachunku,
lokalu, właściciela, externalReference, asset/network, txHash oraz czasu
potwierdzenia. Zachowaj kwotę atomic i opcjonalną kwotę fiat zamrożoną przy
utworzeniu rachunku. Unikalność obejmuje identyfikator dowodu łańcuchowego;
ponowne rozpoznanie transakcji nie tworzy następnego dowodu.
Nie twórz merchantFinancialSale bez pozycji katalogowych. Raport wpływów
pokazuje EXTERNAL osobno, raport sprzedaży/produktów/marży pomija EXTERNAL.
Zamknięcie dnia pokazuje liczbę i sumę wpływów zewnętrznych oraz otwarte
zobowiązania do zwrotu. Płatność bez ceny fiat ma fiat=null, nie0 i bez kursu
z chwili czytania raportu. W API v1 klucz nie zleca zwrotów; właściciel ma
odnośnik do istniejącego procesu zwrotu charge/session i podpisuje go sam.
Jeśli ten proces nie obsługuje nowego rachunku, doprowadź go do działania
przed udostępnieniem API. Potwierdzony zwrot tworzy odrębny dowód wskazujący
EXTERNAL_RECEIPT; zmniejsza netto wpływów EXTERNAL, nie sprzedaż produktów.

Przykład kontrolny: katalogowa sprzedaż fiat1000 i zewnętrzny wpływ z
zamrożonym fiat600 → sprzedaż produktów1000, wpływy EXTERNAL600.
Po pełnym zwrocie EXTERNAL600: sprzedaż produktów1000, EXTERNAL brutto600,
zwroty EXTERNAL600, netto EXTERNAL0. Atomic według aktywów pozostaje osobno.
Nie sumuj wartości atomic z fiat. Dla danych bez wyceny pokazuj niepełność
sumy fiat. W tym przykładzie katalogowy i zewnętrzny dokument muszą mieć
różne transakcje; jedna transakcja nie rozlicza dwóch niezależnych rachunków.
